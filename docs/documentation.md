# 文档维护规则

文档主要用于确定模块划分，帮助理解模块提供什么能力、与哪些模块相关、为什么相关，并通过核心类和入口为后续工作指路。AI 主动维护这些信息；具体实现随时查阅源码与测试，确有必要展开的内部主题按需拆为子文档。

## 什么时候更新

| 触发情况 | 本次工作中需要做什么 |
| --- | --- |
| 用户明确确认了新的方向、边界或协作偏好 | 更新对应约定；尚未落地的内容标明为约定或待实现，不宣称功能已存在 |
| 模块职责、主要能力、关联关系或关键业务语义发生变化 | 同步更新所属文档，并核对相关模块的说明 |
| 核心类或入口新增、改名、移动、删除，或子文档所述内部设计发生变化 | 核对并同步更新简述、源码链接及相关父子文档，修正或删除过时内容 |
| 新增或改变安装、运行、配置、验证方式及依赖要求 | 更新实际可用的命令和前提；移除已失效的说明 |
| 排查过程中发现错误、过时内容、重复规则或失效链接 | 事实可核实时主动修正；无法确认的语义先澄清 |
| 内容超出原文档职责或已经难以快速阅读 | 按主题拆分，更新导航和链接，删除原位置的重复内容 |
| 仅调整字段、函数签名、算法、内部流程或测试细节，现有概览和子文档仍准确 | 修改源码与测试，不向文档追加细节 |

开始工作时阅读相关文档；过程中记录已确认的约束与行为变化；交付前检查文档是否与最终实现一致。验证结果影响使用方式时同步说明，临时测试输出和开发过程留在对话中。

## 写什么、写到什么程度

- `README.md` 维护项目当前能力、必要的运行配置和使用入口；`AGENTS.md` 保留短小的全局规则与导航；架构文档确定整体划分，模块文档介绍职责、能力与关系。
- 模块文档重点回答：负责什么、不属于它的职责是什么、提供哪些主要能力、关联哪些模块以及为什么相关。每个大模块列出少量核心类，附简短职责说明和源码链接；以接口或函数为核心的模块列出对应契约或入口，不为文档新增类。不枚举全部符号，也不要求机械套用模板或为每个目录建立文档。
- 优先修正、替换和删除已有内容，避免每次只追加。区分当前实现、已确认约定和尚未决定的建议；建议不能直接成为强制规则。
- 新增长期规范应有持续适用的原因，并与用户已确认方向一致；单次故障或临时处理通常只需修改代码、测试或局部说明。
- 模块概览只保留影响模块协作的关键业务约定与限制。内部设计若存在仅靠源码不易理解、且对后续维护有持续价值的主题，可在子文档说明其设计原因、协作机制或关键约束；字段清单、函数签名、接口逐项说明、测试用例枚举和逐次修复过程仍留在源码、测试或对话中。
- 每个事实或规则只有一个主要维护位置，其他文档通过链接引用；文档使用中文，代码标识符使用英文。
- `vendor/pi` 是项目已有代码资产，文档记录当前能力和使用方式，随实现维护；不额外维护来源、原始版本基线或修改台账。许可证、版权及第三方声明保留。

## 容量与拆分

不为凑齐文档体系预建目录。出现独立主题、长篇操作细节，或入口文档已经难以快速掌握时，先精简重复内容；仍然过长则拆分。

- `AGENTS.md` 优先保持为短篇规则与导航。详细规范移到对应主题文档，只在入口保留必要提醒和链接。
- 架构总览保留模块关系与共同约束；某个模块的细节过多时，按需迁入模块说明，例如 `docs/modules/runtime.md`。
- 模块内部确需展开的主题单独建立子文档，由模块概览链接进入，子文档链接回所属模块。相关实现变化时在同次工作中核对父子文档与源码，确保内容正确；主题失去维护价值时精简或删除。
- 一个文档聚焦一个主题。拆分时同步更新入口与引用，移走原内容，不维护两份相同正文。
- 不以固定字数机械拆分；以职责是否集中、信息是否易查找为准，也不为普通小修改新增文件。

## 什么时候询问用户

事实同步、纠错、链接修复和不改变含义的拆分可以自主完成。以下情况在修改相关约定前询问用户，并说明具体分歧或取舍：

- 新要求与现有约定冲突，且无法从用户最新指示判断如何取舍。
- 准备新增或改变会影响未来开发方式、业务含义、模块职责、权限或数据保留方式的规范，但现有授权不足以确定方向。
- 文档与代码不一致，无法判断应该修正文档还是改变实现。

用户已经明确确认的方向直接落实，不重复请求确认。澄清期间继续完成不依赖该决定的工作。
